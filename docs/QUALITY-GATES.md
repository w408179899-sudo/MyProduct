# 四个目标的验收依据

目标是让新项目集中实现领域数据、读取映射和业务模块，并能持续升级公共底座。下面列出可检查的依据；通过一项不能替代其他项。

| 目标 | 模板提供的机制 | 当前可执行的验证 | 仍需具体项目证明 |
|---|---|---|---|
| 可维护 | Domain/Application/Infrastructure 分层；有类型的装配、参数和错误；公共包版本固定 | 架构依赖检查、严格配置/迁移测试、实际 NuGet 消费者测试 | 每个业务模块职责和规模；升级后的业务回归 |
| 可扩展 | 每会话独立通道与模块；Mock/硬件同契约；分区读与分区回放；控制台和桌面宿主 | 新名字生成项目接入四层合成夹具，贯穿实际注册入口、正式快照、模块动作反馈和停止；保留分层检查 | 目标游戏读取映射、字段合法性、模块协作 |
| 稳定 | 正式快照唯一发布；生命周期失效；失败保留；故障后清理重试；输入租约 | 冷启动/部分读/取消/并发/重连/清理异常测试；含读取和输入故障的持续负载 | 指定 DLL、固件、DMA/KMBox 的真实断连、进程替换、模块变化和长时间运行 |
| 效率 | 同键采集复用；有界 native 队列；协作预算；异步日志；受限模块数 | 缓存读取分配与 P99 门槛、集合规模样本、1/4/8 账号进展与 CPU、持续负载保留内存/句柄 | 实际通道数量、字段规模、业务算法、物理读取延迟和输入频率 |

本机结果见 [VALIDATION.md](VALIDATION.md)，命令见 [TESTING.md](TESTING.md)。时间、CPU、分配和资源指标必须带测量场景；不能把合成等待负载外推为具体游戏性能。

尚未完成的外部验收按 [HARDWARE-ACCEPTANCE.md](HARDWARE-ACCEPTANCE.md)执行。先验证可控目标的数据读取，再验证输入和恢复，最后按真实账号数持续运行。成功发送输入命令与业务动作实际完成分别验证。
