# DMA 设备绑定

`devindex` 是驱动当前设备列表的索引，不是永久设备编号。普通 Windows USB 注册表清单不提供可靠的 VMM 索引映射。
Roadhog 的设备选择/保存思路可以借鉴，但它将注册表结果按绑定键排序后推算索引的实现没有移入 Smart。

## 保存与核验

桌面编辑账号时选择 Hardware、填写 VMM 库路径和同目录驱动文件名，然后点击“绑定 DMA”。
列表来自 D3XX 的 `FT_CreateDeviceInfoList` / `FT_GetDeviceInfoDetail`，保留驱动原始索引；不会打开 DMA 设备。
用户根据序列号和位置选定一行，保存到编辑项后还需保存账号配置。

绑定保存设备身份、选择的索引、完整有序设备列表 SHA256、驱动文件名与 SHA256。
连接前重新枚举两次；索引不一致、设备缺失、可见拓扑变化、枚举途中变化、身份字段不完整或驱动变化都会拒绝受保护连接。
所选设备的序列号必须在完整列表中唯一。重复序列号即使位置不同也拒绝；位置存在不能证明两块同序列板卡没有对调。
这类设备可以明确保留人工确认的旧配置，但不宣称获得固定设备保护。
成功的核验 guard 持有 D3XX DLL 引用，在 VMM 关闭后才释放，防止核验和打开使用不同的已加载模块。

受保护 URI 目前只支持 `fpga://ft601=1,devindex=N`（参数可交换顺序），不支持 FT2232、UDP、custom driver 或其他可改变后端选择的参数。
索引必须使用没有前导零的十进制；额外 VMM 参数仅允许 `-printf/-v/-vv/-vvv`，不能让远程参数把本机绑定用于另一台机器。
若同目录、当前进程或默认加载路径还存在另一种可加载的 `FTD3XX.dll` / `FTD3XXWU.dll`，会拒绝受保护连接；
LeechCore 会在两种驱动之间回退，不能未经核验就认定两个列表具有同样的索引。
DLL 文件保持由部署方提供；框架不下载、替换驱动或修改已有 Roadhog 目录。

## 运行边界

旧配置的 `Binding=null` 保持兼容，界面明确显示“未绑定：devindex 对应设备仍需人工确认”。
没有自动补绑、偷偷改写索引或绑定失败后退回旧模式的路径。清除绑定是显式编辑操作。

FTDI 文档规定，设备被其他进程占用时，枚举可能只有 Opened 标志而没有身份信息。
此时无法核验就拒绝，可能需要在设备空闲窗口完成绑定；不能把空身份视为原来的设备。
核验要求完整拓扑中每一块板卡的身份都可读，因此即使选中的设备空闲，另一块板卡被 Roadhog 等进程占用且身份不可见，也会阻止捕获绑定。
设备打开后的核验必须在持有设备的 native worker 内完成，父进程再次枚举不能代替它。

账号运行中的 VMM 调用和绑定核验使用隔离 worker；桌面“绑定 DMA”主动枚举目前通过 `Task.Run` 在 Desktop 进程内调用 D3XX，尚未纳入该隔离边界。
这次枚举不会打开设备，但若驱动枚举本身永久阻塞或发生原生崩溃，运行时 worker 的超时及终止机制不能恢复这次桌面调用。

绑定基于驱动实际可见身份和拓扑，不是不可伪造的板卡认证；两次检查之间不可观测的变化不能由轮询保证发现。
本轮离线回归使用伪 D3XX 数据，证明拒绝规则、生命周期和配置往返；没有执行真实枚举、拔插或硬件连接验收。

## 实现依据

- [LeechCore v2.22 FPGA 实现](https://github.com/ufrisk/LeechCore/blob/v2.22/leechcore/device_fpga.c)：FT601 使用指定索引及 `FT_OPEN_BY_INDEX` 打开，FT601/WU 与 legacy 驱动具有回退路径。
- [FTDI D3XX Programmer's Guide](https://ftdichip.com/wp-content/uploads/2020/08/AN_379-D3xx-Programmers-Guide.pdf)：索引枚举、设备身份字段及跨进程占用时的信息限制。

`DmaSettings` 原来的六参数构造器和解构保持不变；`Binding`、`Worker` 为新增 init 属性。
原配置和新配置可直接反序列化；桌面修改其他字段时保留已有绑定和高级 worker 参数。
