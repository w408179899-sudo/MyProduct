# 战斗流程双版本

## 适用范围

第一阶段替换定点战斗 Tick 中的坐下、资源补给与防御选怪交接。新版入口为
`Application/CombatFlow/StationaryRecoveryCoordinator.cs`，旧分支仍保留在
`StationaryCombatController.LegacyTick.cs`。2026-11-17扩展到下述四个边界；
技能释放器、拾取/移动/复活动作、交易提交协议和快照发布本身仍沿用现有实现。

2026-11-16 长跑修复另外增加 `SemiAutoCombatController.CoordinatedSummon.cs`：
仅在 V2 中安排宠物缺失期间的角色回血与重召交接，旧版的召唤顺序保留。

协调器不持有跨 Tick 状态，不访问硬件或底层读取接口。适配器调用现有动作，
并在动作后读取当前状态。结果显式表示 `Continue` 或 `Wait`、坐下许可、唤醒目标、
防御目标与原因；`Wait` 不表示动作成功。每个异步动作返回后检查停止令牌，
即使动作忽略了取消，也不能继续交给下一个动作。

## 选择与回退

- 账号总览的“战斗逻辑”可选“稳定版”或“新版（试用）”，下次启动生效。
- 老配置缺少 `CombatFlowVersion` 时默认 `Legacy = 0`，新版为 `CoordinatedV2 = 1`。
- 版本保存在账号层，不随共享技能方案传播。
- 每次账号启动解析一次有效版本，运行中保持固定。状态显示实际版本，
  不以保存的偏好冒充当前版本。
- 主界面的“战斗版本”入口可执行“全部恢复稳定版”：先原子保存全局策略，
  再通过正常停止路径停止实际运行新版的账号。已经运行稳定版的账号保持运行。
- 回退不会自动重启账号。核对游戏中未完成的交易后，点击账号“启动”进入稳定版。
  显式停止会清除自动恢复意图；不会把尚未确认的交易变成可重复执行的请求。
- 全局策略位于账号配置旁的 `combat-flow-policy.json`，`ForceLegacy = true`
  高于账号选择。损坏或不可读的策略记录警告并使用稳定版。
- “恢复按账号选择”只解除全局覆盖，下次启动才应用账号偏好。
- 重复执行回退是幂等的：已回到稳定版的账号不会再次被停止。

同一账号不允许同时启动两套输入执行器。新版试用使用独立目录时，必须先在原
主界面停止该账号，确认 worker 退出和自动运行意图清除，再由独立程序启动。
直接结束 worker 进程可能触发原主界面自动恢复，不能代替正常停止。

## 保留的业务边界

- 正在攻击角色或宠物的威胁禁止坐下，但不阻止正常回血技能和回蓝药水。
- 起身必须遵守已有确认，不能因为发了 `X` 就继续执行。
- 威胁死亡、消失或转向其他目标后，不能让遗留防御标志永久阻塞恢复。
- 普通附近怪物、采集、领队保护、临时换目标保护及拾取后的等待保留原有优先级。
- 旧动作的超时与重试语义不在本阶段调整，避免把行为变化混入结构重构。
- 公共底层仍被双版本共用；涉及公共层的未来变更必须另外验证并保留稳定安装包。

## V2 宠物重召与角色回血

长跑记录发现：宠物缺失时，worker 等待重召会跳过普通维护入口，连续失败时可能长期
轮不到角色回血。V2 在首次重召前及召唤确认超时后的间隙，为账号已配置且可用的 HP
规则提供一次执行机会。规则的血量阈值、运行时机、冷却校准和每次吸血前的活目标校验仍生效。

正在等待召唤确认时不插入回血按键；确认窗口结束后才交接。HP 动作沿用原来的有限确认，
完成后遵守维护按键间隔。即使回血未确认，下一轮也先给召唤一次机会，防止回血反过来
永久阻塞重召。宠物恢复后重置这一轮交接状态。MP、状态补充和坐下不抢占这个 HP 入口。

此处一个账号状态位只记录“本轮已给过 HP 执行机会”，不把发出按键当成回血成功。
`combat_flow.summon.hp_turn` 用来追踪交接，具体施放结果仍查看原有维护确认和目标保护日志。
该修复不承诺消除全部死亡，也不改变 Legacy 的顺序或共享动作的确认实现。

## 验证与诊断

现有测试用例和断言保持不变。新增用例独立覆盖新版场景、新旧执行痕迹对照、
每个异步边界的取消、策略持久化、配置隔离、有效版本固定、全局回退和停止竞态。
测试执行器对零匹配过滤返回失败，防止把没有执行用例报告成通过。

`worker.loop.enter` 的 `combatFlowVersion` 记录实际启动版本。
新版交接记录 `combat_flow.recovery.decision`，包含 disposition、reason、allowsSit、
wakeTarget 和 defenseTarget；同原因限频记录。

`combat_flow.health.observed` 仅在 V2 的生命守护及拾取阶段边界记录已有玩家快照，
包括血量、`playerCapturedAt`、战斗/拾取/复活阶段和当前目标身份。同一边界限频500ms，
边界键仅用固定名称或步骤枚举。诊断不额外读取游戏、不发输入、不改变恢复和战斗顺序。
同一轮拾取可能复用快照，分析时必须看原始快照时间，不能把每条日志当成一次新读数。

实机验收需要记录观察时长、击杀/拾取/补给进展、错误与预算让步、进程唯一性，
并验证新版停止后旧版重新启动。既有 provider Partial/fallback 警告须结合实际进展
判断，不能将警告数量为零当作稳定标准。

本文件描述实现契约，具体构建、用例数量和实机结果见交付时的验证记录。

## 2026-11-17：宠物回血等待中的紧急交接

V2在`SemiAutoCombatController.CoordinatedPetHp.cs`处理两个宠物回血规则之间的交接。
已有回血尚未确认、宝宝继续掉血进入更低阈值时，重新评估该更紧急规则；只有技能不同、
按键已绑定、宝宝身份与存活一致、人物达到该规则血量限制且真实冷却可用，才可能接管。
同阈值或更高阈值规则不能反向接管，防止两个技能来回切换。Legacy沿用原确认流程。

交接前保留现有冷却确认窗口，至少1500ms，且不短于配置的ConfirmTimeoutMs和按键抑制间隔。
窗口按单调时钟计算；等待更紧急技能时不继续重复旧按键，避免保护窗口被不断重置。
当前玩家快照没有实时读条字段，因此这是一段有限输入保护时间，不等价于实时施法检测。

临近输入再次读取候选技能及玩家/宝宝快照，复核规则、血量、身份与冷却。
成功交付按键后，确认归属才转移给新技能，并沿用原等待期限；期限不足以容纳保护窗口时不交接。
拒绝输入、临时条件失效不会伪造回血成功，也不会丢失原等待状态；停止及读取异常继续向外传播。
日志`semi_auto.spiritmaster.pet_hp.handoff`记录旧/新技能、重试次数、双方血量、保护窗口和剩余期限。

该修改针对已复现的“一个回血规则挡住另一个更紧急回血规则”。原有血量上涨确认语义、
回蓝流程、召唤确认协议保持原样，不将这次交接修复视作全部死亡或施放失败原因已消除。
回归新增在`CoordinatedPetHpHandoffTests.cs`，原测试场景、断言、阈值不改。

## 2026-11-17：召唤超时后的防御交接

实机在切换频道后失去宝宝，连续重召期间遭到怪物攻击。原正常工作入口被重召占用，
即使确认超时并完成一次HP维护，也无法进入定点防御。复活返程已有防御能力，
本次让V2正常定点流程在召唤超时后调用该能力。

`EnsureCoordinatedSpiritmasterPetAsync`保留第一次召唤和待确认期间的输入所有权。
超时释放后，先给原HP维护一次机会，再调用可选的防御处理；没有来袭目标时继续原重召节奏。
宝宝出现、角色死亡或关闭精灵逻辑时清除本轮交接状态。Legacy不调用新增处理。

`StationaryCombatController.CoordinatedSummonDefense.cs`只接管正常定点流程中的实际防御目标，
不启用返程清路，也不把附近普通怪当成威胁。防御期间通过有`finally`清理的作用域标记，
抑制战斗内部再次重召；普通角色攻击仍使用原技能可用性和宠物依赖检查。怪物死亡后归还控制。
新读到角色死亡时直接结束本轮，避免依据此前的存活快照继续发召唤按键。

`combat_flow.summon.defense_turn`和`stationary_combat.recovery_defense.target_selected`的
`pet_recovery`阶段用于核对交接。新增`CoordinatedSummonDefenseTests.cs`，保留所有原测试。
这项修复解决重召重试阻塞防御；召唤最初未成功的游戏内原因仍需实机证据，不能由超时事件单独确定。
## 2026-11-17：召唤冷却与施法确认分开

用户补充：宝宝死亡、消失、切图或远距离传送后，召唤技能有5秒CD。
实机只读接口确认脚本6的Alt+OemMinus是1696（召唤:火之精灵IV），CD为5000ms；
前置1778（服从的手印I）的CD为60000ms。技能数据中的正常召唤施法时间为4500ms。

V2通过`SemiAutoCombatController.SummonCooldown.cs`处理召唤前的冷却：

- 显式技能按ID读取；只有手动键时，从当前官方快捷栏快照定位实际技能，再按ID读取冷却。
  只读取绑定，不修改用户设置；无法解析的旧手动键保留原有有限重试行为。
- 冷却等待不发送召唤键、不占用召唤尝试间隔，也不开始施法确认窗口；HP维护和实际攻击者防御可以执行。
- 已校准时钟时按实际CD判断，召唤不沿用普通攻击提前80ms就绪的容差。尚未校准且存在非零冷却终点时，用有效技能快照的冷却时长作保守等待，
  使用单调时钟；相同终点不反复延长，终点变化或新的宝宝消失阶段重新观察。已确认就绪的技能不额外等待5秒。
- 可选加速技能在CD或尚不能确认就绪时跳过，允许正常召唤；按召唤键前再次核对CD和人物存活。
- 只有召唤输入交付成功才开始原有宝宝出现确认。输入被拒绝时保留重试节奏，并允许防御，
  不把它当作正在施法。`cooldown_wait`、`speed_skipped`和防御原因分别记录，避免把正常CD记成召唤失败。

这些规则仅用于CoordinatedV2；Legacy保留。正常输入后等待宝宝出现的既有保护窗口不被CD检查打断。

## 2026-11-17：精灵技能共用宝宝前置条件

`SpiritmasterSkillEligibility`只判断技能对自己宝宝的依赖，不负责优先级、按键或读外部数据。
`MyPet`目标元数据、命令技能名称及精灵吸收要求自己的宝宝存活；精确的`Summon`效果要求没有存活宝宝。
`SummonHoming`能量攻击及召唤加速增益不归为持续宝宝召唤，避免误拦技能。

仅在CoordinatedV2且开启精灵逻辑时启用新增条件，已知其他职业不进入该条件。Legacy保留已有命令检查及原维护协议。

- 快捷栏候选、连招和待重试动作复用抑制策略，在选择和最后按键边界刷新宝宝状态。
  普通技能入口中的宝宝召唤也必须确认CD完全结束，不使用提前80ms的普通攻击容差或未校准时的试按。
- HP/MP、DP和状态维护先跳过不满足条件的规则，允许后续可用规则执行；实际按键和重试再次检查。
  同一次维护尝试绑定自己的宝宝身份，宝宝死亡、消失或更换后退出，不对新宝宝续用旧重试。
- 起手技能、延迟重试、精灵攻击命令键同样检查；宝宝出现后自动召唤会在准备和实际召唤键之间再次退出。
- 使用已有官方快照。手动配置的技能键可读取当前快捷栏上的技能条件，不改写用户配置；没有映射的键保留原有契约。
- `combat_flow.pet_skill.blocked`区分`pet_missing`、`pet_changed`、`pet_already_present`和`summon_not_ready`，
  正常前置条件失效不记为施法确认超时，也不停止账号。

新增`CoordinatedPetSkillEligibilityTests`覆盖以上边界；原有测试场景和断言不变。

## 2026-11-17：宝宝回血释放证据与回蓝让位

本次实机在19:48和20:23出现宝宝濒死后消失。期间有小幅血量回升确认，但独立技能采样没有观察到相应回血技能CD推进；
第二段还出现精灵吸收每轮约6秒的重复尝试。不能把小幅回血归因为本次技能成功，也不能让一轮回蓝确认隔离宝宝状态变化。

V2的宝宝回血保留按键前的准确技能CD终点；只有该技能CD向前推进、且同一宝宝出现后续血量上涨，才记录`pet_hp_confirmed`。
两项证据可先后到达，已观察的释放证据随当前确认保留，重试不覆盖最初CD基线，交接到另一技能时重新建立证据。
仅CD推进继续等待回血，期间仍可按既有规则交给更紧急的宝宝回血技能；仅血量上涨且仍在维护门槛内继续确认，
超过门槛则按“不再需要维护”取消，不声称技能成功。原人物安全线、生命周期取消、有限确认期限和Legacy契约保留。

`SemiAutoCombatController.PetHpRelease.cs`负责释放证据，`SemiAutoCombatController.MpPetHpHandoff.cs`负责回蓝重试让位。
每次MP技能按键前都检查自己宝宝和配置的回血条件；存在满足血量、人物安全线及CD的规则时，停止本轮MP重试并执行回血，
随后由宝宝确认流程接管，不在同一调用中继续回蓝。没有可用回血技能时保留MP流程；人物HP维护不被此MP专属规则抢占。

诊断新增`combat_flow.pet_hp.release_observed`、`combat_flow.pet_hp.hp_rise_without_release`及
`combat_flow.maintenance.pet_hp_handoff`，并记录CD基线和宝宝距离，供实机区分回血结果、技能释放与让位。
