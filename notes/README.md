# MapleStory 项目笔记

这个目录用于记录 MapleStory 项目的调查记录、架构决策、API 发现、UI 设计、测试结论和交接信息。

## 当前已知信息

- MapleStory 项目是一个 2D 横版游戏项目。
- 角色技能通常都有明确的技能范围大小，例如横向距离、纵向高度、前后判定、命中区域或持续区域。
- 技能通常有朝向，释放时需要考虑角色面向左还是右。
- 技能范围不是一条线，而是一个二维命中区域。例如 X 轴技能可能覆盖前方一定距离，同时对 Y 轴上下约一定范围内的怪物生效。
- 后续技能范围应按 hitbox/area 建模，例如 `range_x`、`range_y_up`、`range_y_down`、`origin_offset`、`facing`、`shape`，而不是只用单一距离。
- 技能命中判断需要同时考虑 X/Y 坐标、角色朝向、技能原点偏移和怪物体积。
- 怪物也不是一个点，怪物本身有体积/碰撞盒。
- 怪物位置数据如果只提供中心点或脚底点，后续需要结合怪物宽高、碰撞盒、受击盒来换算真实占用区域。
- 技能命中、身体接触伤害、怪物避让、平台边缘风险都需要基于角色/怪物 hitbox 判断，不能只按点到点距离判断。
- 技能可以升级，升级后技能数值会变化。
- 技能等级提升可能影响攻击距离、攻击范围、伤害、蓝量消耗、冷却、命中次数、目标数量、持续时间、动作时间或附加效果。
- 技能数据不能只按技能 ID 建模，还需要记录当前技能等级、等级上限、每级参数表和当前加点状态。
- 战斗逻辑后续可能需要计算技能释放后的实际效果，用来提高打怪效率。
- 技能不是按下瞬间立刻命中，通常存在动作前摇或延迟生效。
- 从按下技能键开始计算，大约 0.5 到 1 秒后技能才真正攻击到怪物，具体取决于技能动作。
- 技能效率评估不能只看释放瞬间的怪物位置，还需要预测技能实际生效时怪物的位置。
- 技能效果评估需要关注：当前站位、怪物分布、技能范围、技能冷却、释放耗时、命中数量、击杀收益和移动成本。
- 技能释放决策需要记录或配置：前摇时间、命中时间窗口、动作锁定时间、是否可移动释放、是否会改变角色朝向或位置。
- SkillManager 后续需要能根据当前技能等级计算真实技能参数，而不是使用固定默认值。
- 后续打怪模块不应该只按“最近怪物”或“固定技能顺序”执行，而应该逐步支持基于技能范围和目标分布的效率计算。
- 当前框架先预留两套打怪逻辑入口：即时 tick 打怪逻辑和未来 1-3 秒短期预判打怪逻辑。
- 即时 tick 逻辑用于当前帧反应式决策，例如就近目标、立即释放、紧急处理。
- 预判逻辑用于模拟未来 1-3 秒，评估怪物移动、技能前摇、命中窗口、移动成本、掉台风险和拾取收益。
- 后续两套逻辑可以并存，由 CombatManager 根据账号配置、地图场景或风险等级选择使用。
- 预判逻辑如果做成毫秒级全量轮询，会带来明显 CPU 压力，也会造成 API 请求量过高。
- 正确方向应该是分层频率：Perception 定期读取游戏状态并生成快照，Combat 使用最近快照做本地模拟，不能在每个候选动作里反复请求 API。
- API 轮询应该按数据变化速度分级：角色坐标/血蓝/怪物位置高频，技能等级/装备/地图拓扑低频或变更时刷新。
- 预判计算需要先裁剪候选集，例如只取屏幕内、同平台或技能可能命中的前 N 个怪物和掉落物，避免对全地图对象做模拟。
- 未来 1-3 秒预测应优先使用离散步长，例如 100ms、200ms 或 250ms 一步，而不是每毫秒模拟。
- 预判模块应有 CPU 预算和超时保护，超过预算时退回即时 tick 逻辑，保证脚本稳定。
- 最简单的刷图策略是进入地图后发现怪物就持续攻击，直到怪物清完再做下一步。
- 直接打怪策略实现成本低，适合作为第一版稳定 baseline，也适合在预判模块超时或数据不足时兜底。
- 直接打怪策略的效率上限较低，因为它通常不会主动选择最佳站位、不会利用技能前摇预测、不会并行拾取，也不一定能优化平台移动路径。
- 高效刷图目标应该在 baseline 之上逐步引入：站位选择、技能范围收益评估、未来 1-3 秒短期预判、打怪拾取并行、平台/梯子路径规划和风险控制。
- 地上的掉落物可以一边捡一边攻击，不需要等到打完所有怪物后再拾取。
- 打怪和拾取是可以并行的异步操作，Loot 不应该只建模成“战斗结束后的清理阶段”。
- 后续 Planner/Behavior Tree 需要支持 Combat 与 Loot 同时评估：例如攻击间隙顺路拾取、移动到技能站位途中拾取、低风险掉落优先拾取。
- 拾取决策需要考虑掉落物价值、消失时间、距离、平台位置、当前怪物威胁、技能冷却窗口和移动成本。
- 怪物在平台上的运动轨迹具有随机性，例如可能向左移动 1 秒、向右移动 2 秒，移动方向和持续时间不能简单假设为固定。
- 部分怪物可能从一个平台移动到另一个平台，因此怪物位置预测需要结合平台连通关系，而不是只看当前坐标。
- 角色受到攻击后可能被击退，击退可能导致角色偏离原站位，甚至掉下平台。
- 伤害机制类似超级玛丽一类横版游戏：角色身体接触到怪物就会受到伤害。
- 除了身体接触，角色也可能受到怪物远程技能、地图机关、陷阱或环境伤害。
- 角色受到伤害后大约有 1 秒无敌时间；这个无敌窗口会影响继续站位、穿怪、撤退和补血判断。
- 战斗和导航逻辑需要考虑受击风险、平台边缘风险、掉台检测和掉台后的恢复路径。
- 后续效率计算不能只评估“技能命中多少怪”，还要评估释放位置是否安全、是否容易被击退、是否会因掉台导致总效率下降。
- 后续 Safety/Combat 需要记录最近受伤时间，用于判断是否处于无敌窗口、是否需要暂停进攻、是否可以利用无敌时间穿过危险区域。
- 角色跳跃存在惯性，起跳后角色的水平速度、落点和停止位置不能简单按瞬时坐标处理。
- 角色在跳跃空中仍然可以移动，也就是空中可以继续通过输入改变角色位置和移动轨迹。
- 因为空中可控移动存在，跳跃不应该被建模成固定抛物线，而应该建模成“起跳 + 空中方向控制 + 落地修正”的可控动作。
- 部分装备会影响角色移动性能，例如移动速度、跳跃高度、跳跃距离、空中控制能力或落地后的调整能力。
- Navigation 和 Combat 不能把移动速度、跳跃高度等参数当成固定常量，后续需要从角色状态/装备状态中读取或估算。
- 装备变化后需要重新评估可达平台、跳跃成功率、站位安全距离、技能释放位置和地图刷怪路线。
- 跳跃惯性需要记录，因为它会影响平台间移动、跳跃避怪、技能站位、掉台风险和路径规划。
- 后续 Navigation 不能只做静态点到点寻路，还需要逐步建模跳跃动作的起跳点、方向、水平速度、落点范围、失败恢复和平台边缘安全距离。
- 地图上存在梯子类型地形，梯子需要单独建模为可攀爬连接，不等同于普通平台。
- 上梯子操作大致为：靠近梯子后按向上按钮，然后按一下跳跃才能上去。
- 角色在梯子上按左右方向键并按跳跃，会从梯子上跳下来。
- 从梯子跳下后的落地轨迹遵循抛物线，但具体重力加速度、初速度、水平控制能力需要实测。
- 后续 Navigation 需要记录梯子的入口点、出口点、可攀爬方向、上梯动作、下梯动作、跳离梯子的落点范围和失败恢复路径。

## 新增背景：梯子上平台时机与智能打怪开关

- 如果角色需要通过梯子上到一个平台打怪，平台上的怪物仍然会持续移动，因此不能只判断“梯子可达”。
- 梯子和平台的交点位置属于高风险位置：角色刚上平台时可能立刻接触怪物、受到远程攻击或被击退掉下平台。
- 智能逻辑需要提前计算比较合适的上平台时机，例如预测未来 1-3 秒内怪物是否会远离梯子出口、技能是否能覆盖、角色是否容易被击退。
- 如果完全安全的时机不存在，也应该选择相对最低风险的时机上平台，而不是盲目上去。
- 梯子出口安全评估需要考虑：怪物 hitbox、怪物移动方向、技能前摇、角色上梯动作耗时、平台边缘距离、受击击退方向、掉台恢复成本。
- 智能打怪应先作为脚本设置里的开关预案：勾选“智能打怪”时，额外启用这些预判和风险评估；未勾选时，使用更简单稳定的即时 tick/baseline 逻辑。
- 当前框架已预留账号级智能打怪开关：开启后走 predictive，关闭后走 immediate/baseline。

## 智能打怪算法方向

- 外层流程适合使用 Behavior Tree / FSM：负责打怪、拾取、补给、避险、上梯子、换平台、掉台恢复、死亡/异常处理等大状态切换。
- 动作选择适合使用 Utility AI：给每个候选动作评分，例如当前站位释放技能、移动后释放技能、上梯子、下跳、拾取、退避、补血。
- 评分可以按收益和成本拆分：收益包括命中怪物数量、预期击杀收益、掉落收益；成本包括移动耗时、蓝耗、技能冷却、受伤风险、掉台风险。
- 未来 1-3 秒预判适合使用简化版 MPC / Receding Horizon Planning：基于当前快照预测短期未来，枚举候选动作，模拟每个动作的大概结果，选择评分最高的动作，只执行第一小步，下一 tick 再重新预测。
- 地图适合建成平台图，而不是普通二维坐标平面。平台图中每条边可以表示走路、跳跃、上梯子、下跳、下落等动作，并记录耗时、成功率、风险和失败恢复成本。
- 怪物随机移动不应该做绝对预测，而应该做概率/范围预测：例如 1 秒后可能在某个范围，2 秒后范围更大，再按期望收益或最低风险决策。
- 不建议第一阶段使用强化学习或神经网络。原因是数据难收集、训练成本高、调试困难、多开不可控。第一阶段优先使用规则 + 评分 + 短期模拟。
- 推荐的数据流：`Perception 快照 -> World Predictor 预测未来 1-3 秒 -> Action Generator 生成候选动作 -> Utility Scorer 评分 -> CombatManager 选择动作 -> Executor 执行第一步`。
- 当前框架里的 `immediate_tick` 和 `predictive_tick` 正好对应这条路线：先保留简单即时逻辑作为 baseline，再逐步把 Utility AI 和短期 MPC 填进 predictive 逻辑。

## 性能预算：API 采样与 CPU 压力

- 智能打怪的主要计算压力来自本地 CPU，但真正需要控制的是 API 高频读取、每次读取的数据量，以及多开账号同时采样造成的总请求量。
- 20ms API 采样等于 50Hz。请求量可以按 `账号数 * 每账号采样频率` 粗略估算：1 个账号约 50 次/秒，4 个账号约 200 次/秒，8 个账号约 400 次/秒，12 个账号约 600 次/秒。
- 20ms 采样只适合读取最小核心快照，例如角色坐标、速度、HP/MP、附近怪物轻量列表、附近掉落轻量列表、当前地图或平台状态。
- 不应该在 20ms 采样里执行全量背包扫描、全量技能扫描、全量 UI 扫描、完整地图平台图重建、完整路径搜索或完整 1-3 秒预测。
- 推荐分层频率：
  - 核心运动/战斗数据：20ms-50ms。
  - 怪物/掉落快照：50ms-100ms。
  - 技能冷却/角色状态：100ms-200ms。
  - 背包/装备/任务/UI：500ms-2000ms。
  - 路径规划/平台风险：200ms-1000ms，或事件触发。
- 推荐执行节奏：
  - API 采样 20ms：只采集轻量快照。
  - 即时决策 50ms：处理当前命中、躲避、补刀等快速反应。
  - 智能预判 200ms-500ms：做未来 1-3 秒预测和候选动作评分。
  - 重型规划 500ms-1000ms：处理平台、梯子、路线安全和较大范围移动。
- 多开预算建议：
  - 1-2 开：20ms 核心采样可以接受。
  - 4 开：核心数据 20ms-50ms，其他数据必须分频。
  - 8 开：建议核心采样降到 50ms 左右，预判 200ms-500ms。
  - 12 开以上：必须降频、分批采样、按账号错峰，并允许智能逻辑降级。
- 智能逻辑应只读取 Perception 生成的缓存快照，不应在每个候选动作、每个技能评分或每个怪物预测里反复请求 API。
- 每个账号应有 CPU 时间预算，例如单次智能 tick 尽量控制在 1ms-5ms 内；超过预算时直接退回即时 tick 或 baseline。
- E3-1230 v3 这类 4 核 8 线程 CPU 可以支撑短期预测，但前提是使用快照缓存、分频 tick、候选集裁剪、账号错峰和超时降级。

## 当前 API 验收结论：技能释放与执行通道

- `connect`、`player_info`、`list_nearby`、`list_inventory`、`list_skills`、`list_quickslot` 已能读到真实客户端数据。
- `list_quickslot` 的真实返回结构是 `{ slots = { ... } }`，不是直接返回快捷栏数组。
- 怪物当前可读到 `Id`、`MobId`、`Name`、`x`、`y`；`Hp`、`MaxHp`、`Level` 可能为空，所以第一版击杀判断不能依赖怪物血量。
- 掉落物里 `Source = "mine"` 可以表示自己的掉落，后续拾取判断不能只看 `OwnerCID`。
- `quickslot_use(slot, "press")` 当前不可信：API 返回成功，但实测仍可能只是普通攻击，没有释放快捷栏技能。
- 手动前台按 `Shift` 可以正常释放技能；脚本前台按键路径也已验证可用。
- 后台按键路径当前不可信：适配层可能返回成功，但实测没有产生技能效果。
- 当前默认技能释放策略应走 `PressKey` 原子动作，默认按键为前台 `Shift`，后续允许按账号或方案改成其他键。
- `BasicAttack` 仍保留为兜底动作，但不能把 `quickslot_use` 当作技能释放主路径，除非同事修复 API 后重新验收。

## 第四步：基础打怪最小闭环

- 当前先实现短流程 `maple_probe_basic_combat.lua`，用于实测基础打怪，不直接并入长时间账号 worker。
- 第一版基础闭环为：读取角色和附近怪物 -> 选择最近怪 -> 不在范围内就短距离靠近 -> 范围内停止移动并按技能键 -> 动作后再次读取怪物和掉落变化 -> 有可拾取掉落时执行拾取。
- 第一版不依赖怪物血量，因为当前 API 中怪物 `Hp`、`MaxHp` 可能为空。
- 击杀或攻击效果先通过怪物数量变化、目标 ID 是否消失、掉落数量变化来观察。
- 当前不处理平台、梯子、跳跃、掉台恢复和智能预判；这些属于后续智能打怪阶段。
- 日志必须记录每个 tick 的角色坐标、怪物数量、掉落数量、目标坐标、`dx/dy`、动作 proposal、动作执行结果和动作后的变化。
